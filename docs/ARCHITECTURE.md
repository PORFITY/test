# Архитектура

```
iPhone                                                          Сервер (необязателен)
┌──────────────────────────────────────────────┐             ┌────────────────────────────────┐
│ MealPlanner (SwiftUI)                         │             │ FastAPI backend                 │
│  Views ─ AppStore ─ Services                  │  HTTPS      │  /v1/stores/nearby  (OSM)       │
│   │          │      ├ LocationService (CL)    │ ◄─────────► │  /v1/catalog/offers (адаптеры)  │
│   │          │      ├ StoreSearchService (MK) │             │  /v1/catalog/import (admin)     │
│   │          │      ├ BackendClient           │             │  /v1/ai/intent  (Anthropic)     │
│   │          │      └ Notifications/Keychain  │             │  Адаптеры: Open Prices,         │
│   ▼          ▼                                │             │   импортированные прайсы,       │
│ MealCore (Swift Package, без UI)              │             │   шаблон «сеть с офиц. API»     │
│  • Planner / MenuSolver / Scheduler           │             └────────────────────────────────┘
│  • PackCover (упаковки), OfferBuilder         │
│  • Allergens, Kitchen, Recipes, Assistant     │
│  • StateStore (JSON, офлайн)                  │
└──────────────────────────────────────────────┘
```

## Почему так

* **Вся математика — в MealCore, без UI-зависимостей.** Поэтому оптимизатор, деньги, упаковки, аллергены и хранилище тестируются на Linux
  и macOS (CI) и не зависят от SwiftUI. Приложение — тонкий слой над ним.
* **Оптимизация на устройстве, а не на сервере.** Рацион можно пересчитать без интернета (замена блюда, смена числа людей); приватные данные
  (аллергены, профили) не покидают телефон. Серверу нужны только каталоги, карты и AI.
* **Хранилище — Codable JSON (атомарная запись, `completeFileProtection` на iOS), а не SwiftData/Core Data.** Осознанный выбор: структура
  состояния простая, данные целиком читаются в память, миграции тривиальны, файл можно проверить тестами на Linux, повреждённый файл
  не теряется молча (сохраняется копия). Для будущих больших каталогов на устройстве переход на SwiftData возможен без смены ядра.

## Алгоритм расчёта (MealCore)

1. **Фильтры (строгие):** аллергены (по справочнику ингредиентов и составу каждого товара, включая «может содержать»), нежелательные
   продукты, тип питания, техника и посуда (`Kitchen.batches`: источник тепла, набор посуды, вместимость → «подходов»), наличие цены/запаса.
2. **Предложения (`OfferBuilder`):** товар → ингредиент (`ProductMatcher`: основы слов + исключения, «рисовая мука» ≠ рис), размер упаковки
   (`PackageSizeParser`: г/кг/мл/л/шт/мультипак), акционная цена, аллергены, свежесть цены. Неопознанные, без цены/размера, не в наличии — отбрасываются
   с причиной, цена никогда не достраивается.
3. **Покрытие упаковками (`PackCover`):** минимальная стоимость, чтобы набрать ≥ N единиц целыми упаковками (точный DP «неограниченный рюкзак»;
   для очень больших N — лучшая по цене за единицу упаковка + точный DP на остаток). Проверено перебором на случайных инстансах.
   Рис 150 г при упаковке 900 г за 130 ₽ стоит 130 ₽; остаток 750 г учитывается в следующих блюдах.
4. **Меню (`MenuSolver`):** слот = (день, приём пищи); выбор = (рецепт, масштаб порции 1…2). Цель:
   `λ·стоимость_закупки(упаковки) + штрафы(повторы, соседние слоты, калорийность дня, белок, предпочтения, подходы)`; локальный поиск
   с точным пересчётом дельты и «встряской». Внешний цикл подбирает **минимальное λ, при котором итоговая стоимость укладывается в бюджет**
   (бисекция) — бюджет тратится на разнообразие и любимое, но не превышается. Если и при максимальном λ не укладывается — возвращается план
   со статусом `overBudget`, минимально достижимой суммой и советами (никакой подгонки цифр).
5. **График закупок (`ShoppingScheduler`):** по дням, с учётом остатков/«Моих продуктов» (с датами), срока годности (с заморозкой, если есть морозилка),
   этапов (`stageDays`; для периодов > 14 дней по умолчанию неделя). Скоропортящееся не покупается впрок.
6. **Магазины (`chooseStores`):** кандидаты → жадный выбор набора по `стоимость + штраф за визиты` (время и расстояние) в режимах
   «максимальная экономия / ближайшие / один магазин / баланс».
7. **Независимая проверка (`PlanVerifier`):** пересчитывает суммы, покрытие спроса закупкой, аллергены, нежелательное, технику по готовому плану
   (не использует внутренности оптимизатора). Прогоняется в тестах и перед применением любой замены блюда.

## Ассистент

AI (по желанию, через backend) только превращает фразу в структурированное намерение (`AssistantIntent`). Любое изменение меню выполняет
детерминированный движок: подбор вариантов из проверенной библиотеки → пересчёт плана с закреплением остальных блюд → `PlanVerifier` →
применение. Модель не может ввести цену, граммовку, новый продукт или обойти аллерген. Без сети и без AI работают локальные команды на русском.
Рецепт, предложенный AI/пользователем, проходит `RecipeValidator` (только ингредиенты справочника, разумные количества) и те же фильтры.

## Безопасность и приватность

* Нет секретных ключей в приложении: ключ Anthropic и admin-токен — только в окружении сервера; токен доступа клиента — в Keychain.
* Только HTTPS (App Transport Security по умолчанию; приложение отвергает не-https `BackendBaseURL`).
* Геопозиция — разовый запрос «при использовании», постоянный доступ не запрашивается; есть ручной адрес.
* Данные локальные; «Удалить все мои данные» стирает файл состояния, токен и уведомления.
* Сервер: токен-авторизация, ограничение частоты запросов, жёсткая валидация ответа модели (неизвестные ключи/индексы отбрасываются),
  запросы к внешним API с идентифицирующим User-Agent.
